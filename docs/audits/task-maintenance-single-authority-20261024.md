# 长期任务维护统一权威修复

日期：2026-10-24。范围：电脑端与手机端长期运行维护、TaskRuntime 配置与状态、正式路由装配、共享 TaskHost 编译方式。

## 标准方案

- TaskRuntime 是任务执行与运行状态的唯一权威，控制面复用现有执行器、队列、进程容量、持久化仓储及管理员权限，不建立第二个任务执行系统。
- 配置采用校验、乐观并发控制、事务持久化、提交后应用、执行器回执的完整链路。任务并发配置与统一超时配置同时提交；任意一项失败均回滚。
- 降低并发只限制后续执行，不强杀当前任务。既有插件和任务定义的更细粒度并发限制继续有效。
- 超时复用 operation_timeout_policy，支持禁用，时长为 30 至 1800 秒且为 30 秒的倍数。此策略已经控制模型、工具、媒体等新调用，不新建任务专用超时系统。
- 本地、Cloud Core、Device Agent 使用相同实现，每个服务实例管理自身任务与执行容量。共享 Core 的任务维护属于管理员控制面，保留 SharedCoreAdminOnly、Core 身份、统筹模式及权限版本校验。任务私有输入和结果不返回维护概览。

## 旧功能迁移清单

| 原功能 | 当前实现 |
| --- | --- |
| 运行中或空闲 | TaskRuntime 的活动执行记录和实际本机任务进程 |
| 任务列表和最近活动 | 真实任务 ID、任务定义、状态、执行位置、最近活动时间，最多 50 项并返回截断标识 |
| 最大任务数 | 执行器全局并发上限，同步作用于队列限流和实际进程预留 |
| 超时设置 | 复用已存在的统一超时设置，保存时校验其独立版本 |
| 配置保存与重启恢复 | app_settings 正式存储、版本 CAS、事务后应用和启动重载 |
| 清理临时文件、日志轮转、数据库完整性检查 | 保留原接口与业务实现，增加页面加载时 Core 和权限范围固定 |
| 手机运行时健康与手动检查 | 保留原功能 |

有效旧并发设置只迁移一次；无效旧值使用执行器默认值。已有统一超时设置优先保留；不存在统一设置时，仅迁入符合统一策略范围的有效旧分钟值。原本无效的旧专用超时值不会覆盖已生效的统一策略。旧设置以墓碑退役，保留历史审计信息。

## 清理内容

- 删除旧 conversations/messages SQL 推导任务状态的实现。
- 删除旧 GetLongRunningConfig、GetLongRunningStatus、UpdateLongRunningConfig 和 long-running 管理操作分支。
- 删除 /api/runtime/long-running/config、/status 路由，两端改用 /api/runtime/tasks/config、/status。
- 正式系统路由复用启动时的同一个 SystemService，避免第二实例缺失 TaskRuntime、重复加载全局配置和使用不同的配置锁。
- 电脑端和手机端只接受 source=task-runtime、applied=true 及匹配的配置值和版本回执。

## 正式 TaskHost 编译缺陷

真实任务模拟发现，旧 CommonJS 编译将动态 import(fileURL) 改写为 require(fileURL)，导致正式产物无法加载任务入口。原有 TLS 联测单独使用 ESM 转译，未覆盖正式编译方式。

TaskHost 改用 NodeNext 模块与解析模式，任务类型直接复用 SDK 的 tasks 子模块，保留 Node 原生动态导入。没有重写任务加载器，也没有降低插件文件树、入口摘要或目录边界校验。测试的临时目录统一解析真实路径，适配 macOS /var 到 /private/var 的映射。

## 验证

- 并发配置热应用、实际进程预留、降低并发保留已有任务和数据错误传播。
- 三种运行模式迁移、持久化重载、旧配置退役、事务失败回滚、并发版本冲突及统一超时冲突。
- 正式系统路由共用启动时的任务服务。
- 电脑端真实回执、云端配置范围固定和手机页面保存回执校验。
- 正式 TaskHost 编译后，通过真实 HTTP、SQLite 队列和项目 Node 运行两个任务；全局并发为 1，观察到运行与排队，两个任务的期限为 90 秒，最终结果正确。
- 项目完整 Electron/Core 服务中，保存并发 1 和统一超时 90 秒，验证错误 Core 与旧版本被拒绝；重启后配置恢复正确，再恢复测试前配置。
- 旧维护接口返回 404。生产模拟使用的临时数据库、任务目录由测试生命周期自动清理。
