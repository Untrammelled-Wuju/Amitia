## 复跑隔离桌宠页面

在项目根目录执行准备命令。前端使用项目既有的 5178 开发服务，脚本会把所有业务 HTTP 请求转发到临时 Device Agent。

```bash
qa_project="$PWD"
qa_dir="$(mktemp -d)"
mkdir -p "$qa_dir/config" "$qa_dir/workspace"
cp backend/config/config.yml "$qa_dir/config/"
touch "$qa_dir/.qa-pet-isolated"
printf 'corrupt QA fixture' > "$qa_dir/qa-bad.petx"
ln -s "$qa_project/runtime/plugin-host" "$qa_dir/plugin-host"
ln -s "$qa_project/runtime/task-host" "$qa_dir/task-host"
python3 -B - "$qa_dir" <<'PY'
import pathlib
import runpy
import sys

root = pathlib.Path(sys.argv[1])
build = runpy.run_path("plugins-code/qa-desktop-pet-plugin/build_package.py")["main"]
for name, version in (("good", "1.0.0"), ("update", "1.0.1")):
    build.__globals__.update(
        STAGE=root / ("package-" + name),
        OUTPUT=root / ("qa-" + name + ".petx"),
        PACKAGE_VERSION=version,
    )
    build()
PY
(cd backend && go build -o "$qa_dir/AmitiaCore" ./cmd/server)
(
  cd "$qa_dir"
  AMITIA_RUNTIME_ROOT="$qa_dir" AMITIA_DATA_DIR="$qa_dir" \
    AMITIA_CONFIG_DIR="$qa_dir/config" AMITIA_WORKSPACE_DIR="$qa_dir/workspace" \
    AMITIA_NODE_BIN="$qa_project/AmitiaData/node/bin/node" AMITIA_EXTENSION_DEV_MODE=true \
    ./AmitiaCore --runtime-profile device-agent
)
```

待隔离进程就绪，从另一终端运行 `desktop/node_modules/.bin/electron scripts/test/qa-pet-browser.cjs <qa_dir>`。启动命令仍占用前一终端，可在测试完成后终止该进程。

## 未修复与新增风险

- `POST /api/model/configs` 接受 `{}` 并持久化一条空配置。该记录会出现在模型列表，被激活后对话会以“模型未配置”失败。调用方包含引导流程，引导流程并不提交 `name`，所以“哪些字段必填”需要按提供商类型确定，本轮只记录未改。
- 变更探测中另有 60 余处把“找不到/参数非法”映射成 500 的接口（工作区隔离、角色团队、扩展内核启停、游戏中心急停等）。本轮先修了消息主路径的同类映射，其余已在第四轮按类别处理，见下文“四轮”。
- 关系时间的重逢表达依赖十天以上的真实时间跨度，本轮只验证了状态、设置与普通轮次，未验证重逢触发与抑制。

## 四轮：错误分类——把“找不到”从“服务故障”里拆出来

三轮收尾时留下了同一类缺陷的清单：变更探测 2 682 个请求里 66 个 500、只读探测 1 737 个请求里 12 个 500，全部是“资源不存在 / 参数非法”被当成服务端故障返回。这类 500 最容易被误判成“系统很稳”：进程没崩、日志里有明确原因、接口也确实返回了响应体。但对用户和客户端来说后果是真实的——前端把它当成后端故障去提示和重试，而那个请求永远不会成功。

本轮逐类定位根因（不是逐条改字符串），修复后按同一口径复跑。

剩余 5xx 已全部核对，均不是本轮引入的分类缺陷：

- 62 个 `POST/GET /api/extensions/workflow-devices/:deviceId/...` 返回 503 `host_registry: device not found`。该路由把“设备未登记”和“设备离线”合并成 503，前端只用列表里已知的 deviceId 拼 URL，所以本轮未改语义，仍是待确认项。
- 2 个 `/api/desktop-pets/doctor/status` 返回 503 `blocked`，阻止项是 SurrealDB（`127.0.0.1:0`）与 Qdrant 未初始化——隔离实例没有启动这两个依赖，属环境事实。
- 9 个 `/api/extensions/workflows/:id/ai/*` 返回 502，来自替身模型返回的 `Q…` 非法 JSON，正是 QA-20 想表达的语义（上游不可用），不是新的服务端故障。

本轮改动只修 HTTP 语义与错误传播，不改变任何业务行为；因此“接口现在返回 404”不等于“该功能可用”。另外未运行真实前端页面去确认它对 500→404 的展示变化，这一点没有验证。

## 四轮未修复

- `POST /api/model/configs` 仍接受 `{}` 并持久化空配置（三轮已记录）。
- `workflow-devices` 的“设备未登记”仍返回 503，需要产品确认 404/503 语义后再改。
- `agentplatform.respondError` 与 `workflowDeviceControl` 仍保留字符串启发式分类（`not found`、`读取`、`offline`），本轮只修正了顺序与哨兵识别；剩余分支仍可能把新错误文本分错类。
