## 4. 发现的缺陷

### QA-08（P1）发送失败时用户看不到任何失败原因，助手气泡给出误导文案

- 复现：全新隔离环境、角色列表为空 → 打开对话 → 输入任意文本 → 发送
- 预期：显示「请选择调用角色后发送消息」并提供创建角色入口
- 实际：输入清空、无 toast、无错误行；助手气泡显示「已中断 · 保留已生成内容 · 可继续生成」，但没有任何已生成内容
- 根因：
  1. `front/src/composables/useWebChatSend.ts` 失败分支把助手占位从 `queued` 置为 `interrupted`，用户消息置 `failed`，并把 `modelError` 写入 ref；
  2. `front/src/components/MessagesArea.vue` 只在「最后一条可见消息 `status=failed`」时插入错误行，助手为 `interrupted` 时两个分支都不命中，`modelError` 永远不会渲染；
  3. `front/src/conversation/rendering/AIMessageRenderer.vue` 对 `interrupted` 使用固定文案，零内容时不成立。
- 影响：所有发送前置失败（未选角色、服务未就绪、`refresh` 失败、附件校验失败）都表现为「消息消失 + 无限期无反馈」，用户无法判断发生了什么，只能反复重试。

### QA-09（P1）零角色时输入框仍可发送，且无创建角色引导

- 复现：同 QA-08
- 预期：无角色时禁用发送并提示「先创建角色」
- 实际：可正常输入并点击发送，只产生静默失败；欢迎语仍是通用「你好，我是 AI 陪伴角色」
- 影响：新用户首个动作必然失败且无解释，直接构成首次体验阻断。

### QA-12（P1）macOS 上 SurrealDB 永远无法启动，且原始错误被吞

- 复现：macOS arm64 隔离环境启动 → `/readyz`
- 实际：`provider.graph-store` 恒为 `degraded`，错误文本仅 `wait for surrealdb ready: process amitia.surrealdb is restart-backoff`
- 证据：
  - `desktop/resources/surrealdb/surreal.zip` 内只有 `surreal.exe`（PE32+ Windows x86-64）；
  - 运行时按平台拼出 `surreal`（darwin 无后缀），找不到后才尝试解压 `surreal.zip`、`surreal.exe.zip`；
  - `backend/pkg/database/surrealdb/spec.go` 中 `if err := util.UnzipFile(zipPath, surrealDir); err == nil { break }` 丢弃解压错误；
  - 隔离目录内 `surrealdb/surreal.exe` 113,688,576 字节被解出但不可执行；
  - 对照：`desktop/scripts/prepare-release-runtime-assets.mjs` 有 `expectedBinary` 平台校验，运行时路径无校验。
- 影响：macOS 用户图谱记忆能力永久不可用，且日志与 `/readyz` 都无法定位原因；发布侧与运行侧平台校验口径不一致。

### QA-13（P1）强杀 Core 后 Qdrant 进入不可自恢复的假降级

- 复现：`kill -9 <core pid>` → Core 自动重启
- 实际：Qdrant 首启 panic `Failed to load local shard ...`（exit 101），随后新进程已监听端口，但监督状态固定 `restart-backoff`，`/readyz` 持续 `degraded`，30s 内 6 次轮询无变化；完整重启应用后恢复
- 影响：用户强制结束进程/断电后，向量检索永久降级且无恢复入口；日志只给出 panic，`/readyz` 给出的是进程状态而非根因。

### O-01（P2，观察）`SIGTERM` 停止 Core 后不再被拉起

- 现象：`kill -TERM` 后 Core 未重启，UI 停留在「本机 Core 服务暂不可用」，需重启应用；`SIGKILL` 反而会自动重启
- 影响：进程被安装器/系统优雅终止时用户无法自恢复；行为与强杀不一致，缺少「重启 Core」入口。

### O-02（P3，待复核）路由切换后确认框残留

- 现象：删除记忆确认成功后切换到世界书页，`.el-message-box` 仍 `visible=true`，且再次打开「新增规则」时出现两个弹层节点
- 说明：本次为脚本连同多次点击触发，未能稳定复现，reload 后消失；不计入确认缺陷，列入待复核

## 9. 修复方案（行业标准，已确认并实施）

### 9.1 失败态可见（QA-08 / QA-09）

行业通行做法：失败由「消息级状态 + 行内错误条 + 重试动作」承载，不以「最后一条消息是否 failed」作为渲染条件；只有用户主动中断才使用 `interrupted`。

1. `useWebChatSend.doActualSend` 失败分支：助手占位置为 `failed`（保留 `assistantTurn.error` 原文），用户消息置 `failed`，`modelError` 只作为兜底文案
2. `MessagesArea` 改为按 `lastErrorMessage`（来自失败消息本身或 `modelError`）渲染错误条，并在错误条内提供「重试」；`interrupted` 仅在用户主动停止时出现
3. `AIMessageRenderer` 对「`interrupted` 且内容为空」不再显示「保留已生成内容」
4. 无角色时禁用发送并展示「创建角色」CTA，欢迎语区分「无角色」与「有角色未选」
5. 回归用例：`front` 下新增发送失败渲染断言（失败前后对比）、零角色禁用断言；后端无需改动

### 9.2 平台二进制与原始错误（QA-12）

1. `backend/pkg/database/surrealdb/spec.go`：按 `runtime.GOOS/GOARCH` 期望二进制名校验归档内容；解压失败保留并返回原始 `err`；exec 失败原始错误进入 `/readyz` 组件错误
2. 发布资源构建阶段对 `surrealdb/*.zip` 增加目标平台校验（与 `prepare-release-runtime-assets.mjs` 同口径）
3. 回归用例：构造错误平台归档 → 断言返回包含解压/exec 原始错误的错误链

### 9.3 依赖服务自恢复（QA-13 / O-01）

1. runtimehost 的 `restart-backoff` 增加健康探针回收：进程存活 + 端口可连 + 依赖 `/health` 通过时回置 `ready`
2. 回退次数达上限时，`/readyz` 输出原始 panic 文本，并提供「重建向量库」入口（删除损坏 collection + 从源数据回填）
3. CoreManager 统一退出语义：非正常退出与优雅终止均记录原因；UI 增加「重启本地核心」动作
4. 回归用例：`kill -9` 注入后断言 `restart-backoff` 在探针周期内回置（后端 `runtimehost` 包）

以上三项均涉及源码修改，已按确认后的方案实施，实施结果与回归证据见第 5 节。
