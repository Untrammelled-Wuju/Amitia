# 日程提醒与主动任务统一调度整合方案及开发清单

日期：2026-10-14，Asia/Shanghai。状态：用户要求继续，已开始按方案进行源码整合，尚未完成整体验收。

## 已确认的产品范围

聊天、手动和插件都能创建用户提醒；到期在所属角色对话发送消息，默认发送系统通知，创建时可指定已接入渠道。保留管理、执行历史、一次／每天／每周／每月／自定义间隔／指定星期、时区、暂停及结束条件。

手机和电脑沿用现有“日程提醒”页面，直接补齐功能。插件内部技术调度保留开发者入口，共用调度底座。

补充要求：完整支持本地、设备协同与云端模式；产品名称“主动消息”统一更名为“主动任务”。本次更名保留现有规则、限制、管理与消息发送能力，默认任务动作仍为发送角色消息；不因更名自动扩展为可任意执行脚本或设备操作的任务。

主动任务能力必须作为宿主能力开放给插件，提供 Host API 和 SDK；插件通过统一服务创建和管理任务，在本地、设备协同与云端模式都能调用，不直接访问调度数据库，也不自行维护第二套扫描器。

保留和复用已有源码功能，丢弃旧日程与提醒数据，不转换历史格式，不迁移旧业务记录，不保留旧数据读取或回退链。用户要求继续后开始源码整合；当前没有构建安装包、安装、发布或 Git 上传授权。

## 架构选择

采用单一持久化调度账本、统一提醒业务入口、目标执行适配和持久化投递结果的形式。

以已有 `backend/internal/extension/kernel/schedule` 为唯一调度底座，复用 Kernel SQLite 的 definition、state、trigger、run、lease、retry、circuit、quarantine 记录。用户提醒作为 `user_reminder`、主动任务作为 `proactive_task`、插件内部技术任务作为 `plugin_schedule`，保存在同一账本；现有提醒、角色主动任务和开发者调度入口是相应业务视图，不维护独立计时器或重复执行历史。

`backend/internal/reminder` 收敛为用户提醒业务模块：参数校验、归属、重复规则、创建／管理、查询展示、触发目标和投递结果汇总。它不再使用旧 `reminders` 表、不保留独立 30 秒轮询，不维护另一套执行状态或重复推进算法。

调用链为：

`聊天工具／手机／电脑／插件 → ReminderService → Kernel 调度账本 → 单一调度器 → Reminder 执行适配 → 已有角色对话和消息投递 → 手机／桌面系统通知与渠道结果`。

“一套”指一个提醒 ID、一个权威定义、一套状态机和执行历史、一个到期执行者。对话消息、渠道投递、系统通知各自的既有持久化记录继续承担发送和回执职责，通过触发 ID 关联，不能成为第二份可独立修改的提醒定义。

用户提醒不能伪装成某个已安装插件来通过权限检查。Kernel 需要显式支持宿主用户工作负载，按真实用户／设备／角色主体授权；插件创建仍按真实插件和模块主体授权。插件技术调度的原有权限与生命周期契约保留。

复用既有目标执行适配机制，为用户提醒注册真实的提醒执行目标，例如 `builtin.reminder.fire`，并在容器中绑定 Reminder 执行服务。只存入目标名称、输入模板或工具元数据不算完成接入。定义／输入 Schema、插件 SDK、权限注册和目标可用性检查同步更新，确保创建时即可发现目标未装配。

## 权威数据与操作契约

### 定义与状态

提醒定义至少包含：字符串 ID、工作负载类型、来源、不可由请求伪造的 Space／Owner／角色、绑定对话、标题与内容、时区、重复规则、起止条件、渠道和通知目标、创建请求及来源插件／模块、定义版本和代次。

来源包括聊天、手动、插件；这些是展示和生命周期属性，不能代替授权主体。系统填充 Owner、Space 和插件身份，禁止客户端通过 JSON 自选别人的身份。

Kernel 定义是唯一权威业务记录。为提醒增加的结构化载荷纳入定义哈希与校验，状态记录负责暂停、启用、下次执行和计数；不会再创建一份普通 `reminders` 表作为第二权威来源。暂存请求回执和各阶段投递意图是执行可靠性记录，不是第二份提醒系统。

创建要预先验证重复规则、可计算的下一次时间、实际角色／对话和渠道权限，再在所有者的 Kernel 数据库事务中保存定义、初始状态与幂等确认。当前 `InstallDefinition` 分别保存定义和状态、部分计算错误被忽略的做法需要收敛，失败不能留下“已创建但不能执行”的记录。

更新、暂停、恢复、停用、删除和立即触发均检查显示时的定义版本／代次及当前权限。旧页面操作返回冲突并刷新，不覆盖新设置。暂停或删除后，旧代次的待执行触发不得继续发送。

### 数据归属与跨设备

接入现有 Device Mesh 的认证、数据所有者路由与权限校验。用户提醒保存在创建时确定的合法所有者上；选用本机模式时由所属设备的内置后端执行，选用受委托 Core 时由该 Core 执行。

每次触发前重新验证当前委托、角色、会话和渠道权限。客户端切换 Core 不自动复制提醒到另一所有者；撤销权限、所有者不可达或角色／会话失效时阻断并记录原因。编辑“历史所有者”的数据必须按已有授权访问机制处理，不能靠客户端缓存接管执行。

### 云端模式必须纳入实际运行链

现有 `runtimeprofile.ProfileCloudCore` 已启用业务服务、Extension Kernel、Task Runtime、渠道和持久化事件，但禁用设备执行面、设备插件运行时和本地 UI 能力。统一调度服务必须在云端真实装配、启动、恢复并对外提供认证后的用户管理接口，不能只在本地服务容器注册后宣称支持云端。

| 模式 | 权威账本与到期执行者 | 手机／电脑职责 | 离线行为 |
|---|---|---|---|
| 本地 | 指定本地所有者的持久化 Kernel 账本和内置后端 | 通过相同业务接口管理、展示及接收通知 | 所属后端停止时按统一错过策略恢复 |
| 设备协同／委托 Core | 创建时确认的所有者和当前获授权的执行端 | 按 Device Mesh 路由访问；客户端不另建副本或扫描器 | 所有者不可达时明确等待／阻断，不能让另一个设备静默接管 |
| 云端 Core | 云端持久化账本及云端调度器，在后台独立执行 | 认证后远程管理，接收同步消息、推送和执行状态 | 手机／电脑离线不停止云端任务；云端保存消息和投递结果，客户端按授权恢复同步 |

云端数据按真实 Space、认证用户／设备主体、角色权限和资源归属共同隔离。Core ID 不等于所有用户可以互相读取的授权；不能使用旧 `default`／`local_user` 兼容条件跨主体查任务。普通用户能管理自己的提醒和主动任务，平台管理员操作另有明确范围。

云端定义保存 UTC 计划时间和用户选择的 IANA 时区；不能以云服务器时区替代用户时区。云端程序重启后从持久化账本恢复，不重新生成另一份任务，也不依赖浏览器在线或 Flutter 的页面定时器。

一个所有者的账本只允许当前持有有效租约和执行代次的调度者执行。云端部署先明确持久化存储、单活所有者与恢复责任；如果配置多个副本，必须有经过验证的共享协调／选主能力，不能复制本地 SQLite 文件后让各副本同时扫描。

云端消息生成和渠道发送使用云端实际可用且获授权的提供者；需要原生设备能力的操作通过已授权设备执行路径，并按在线和能力状态处理。云端没有设备执行面时返回明确阻断，不能假装完成设备通知或设备操作。

手机原生通知通过已注册设备和现有 Push／Native 能力接收；桌面客户端使用认证连接和 Electron 通知；纯网页使用浏览器实际支持并获授权的通知方式。不支持后台网页推送时明确提示能力限制，不能用“有云端接口”冒充浏览器离线通知已经接入。

手机离线期间云端可以继续完成业务执行，但设备通知要按提供者结果和有效期记录。恢复时补同步消息与历史，通知去重并遵守补发窗口；不把“云端生成成功”标成所有设备已收到。

手机和电脑可以同时查看同一条提醒，但不同时执行同一个触发。Android 原生机制可以协助唤醒所属内置后端；业务执行仍由同一 Kernel 账本和租约决定，Flutter 定时器或原生闹钟不能再独立生成第二条消息。

### 对外接口

保留现有 `/api/reminders` URL，整体替换为统一业务实现，这属于沿用产品接口，不是历史数据兼容。整理为列表、详情、创建、编辑、暂停、恢复、停用、删除、立即触发、预览、执行历史、状态、队列诊断和历史保留设置。

模型工具、插件 Host API 和 HTTP Handler 只做薄适配，共同调用 ReminderService。普通用户管理自己的提醒不应继续依赖全局管理员门禁；插件内部技术任务的开发者／管理员访问规则保持独立。

两端统一使用字符串 ID 和结构化重复规则、明确时间及版本字段。提供错误码、保存确认、Owner、下一次执行时间和真实状态。空响应、缺少确认、未知时间或无法访问所有者均不得转换成“已成功”或正常空列表。

## 时间规则与建议默认行为

下列边界行为是本方案的建议默认值，随整体方案一并确认：

| 规则 | 实现和行为 |
|---|---|
| 一次 | 使用现有 one-shot；过去的创建时间拒绝，手动立即触发是明确的独立操作 |
| 每天／每周／指定星期 | 按保存的 IANA 时区和当地墙上时钟计算，复用可验证的 Cron 能力；星期按统一的 ISO 表达映射 |
| 每月 | 在 Kernel Calculator 内增加明确的日历规则，保留原始日号锚点；缺少该日时默认取当月最后一天，例如 1 月 31 日 → 2 月末 → 3 月 31 日；不直接用无法表达该规则的简单 Cron |
| 自定义间隔 | 保存间隔与原始锚点，按固定经过时长计算；不与“每天当地几点”的日历规则混用 |
| 时区 | 初始使用创建者当前时区，保存 IANA 名称并展示；更改设备时区不会静默改掉现有提醒时区 |
| 夏令时 | 当地时间不存在时移到下一合法时间；当地时间重复时只执行一次，避免重复发送 |
| 开始／结束 | 支持开始时间、结束时间、最大到期轮次；重试不重复计数，手动立即触发不消耗重复次数 |
| 暂停／恢复 | 保留原始重复锚点；恢复从下一合法未来时间开始，暂停期间不补发 |
| 离线／错过触发 | 默认补发最近一次，建议补发窗口 24 小时；不逐次轰炸补发，超过窗口记为错过／过期并计算未来轮次 |
| 并发／抖动 | 同一提醒不重叠执行；用户提醒默认关闭随机抖动，插件技术任务仍可使用已有策略 |
| 重试 | 复用现有有上限、退避、租约和熔断机制；只重试失败或未确认阶段，不重复生成已保存消息 |

系统无法在所属后端已被操作系统终止且没有可用唤醒机制时保证立即执行。界面须区分计划时间、实际执行时间和错过状态；缺少通知权限、设备离线或渠道不可用要反映实际结果。实现阶段应接入可用的既有后台／原生能力，并进行相应真机验收，不能用页面定时器冒充后台可靠调度。

## 提醒内容、渠道和系统通知

默认绑定创建时的所属角色和合法对话。手动创建时由页面给出当前角色／对话；如果没有可用对话，在保存提醒前调用现有正式会话创建流程并取得确认。执行时找不到绑定对话应阻断并展示原因，不把提醒悄悄发到其他角色最近的会话。

沿用现有角色语气生成提醒的能力，并保留直接提醒内容。模型生成不可用时，建议使用用户已确认的标题／内容构造普通提醒，记录生成降级；没有有效内容时返回失败，不能伪造模型成功。

默认产生所属对话消息和系统通知。用户选择额外渠道时，要解析真实已安装提供者、会话／接收对象和授权，展示渠道不可用、未登录、已排队、提供者接受、明确送达或失败等实际阶段。`all` 等旧工具参数应转为明确的当前业务含义，不能无条件广播到全部渠道。

系统通知沿用 NotificationRuntime 和两端原生通知桥，绑定同一消息／触发 ID，点击跳转到对应角色对话或提醒详情。按既有前台会话抑制和用户通知设置去重。用户拒绝通知权限时保留对话消息，并显示通知未发送；提供者接受不等于用户已读。

当前通知识别依赖 `reminder:` 请求前缀，保留稳定的提醒类型和触发关联，避免统一后被当作普通回复或同时触发两套通知。

## 执行状态和历史

将计划执行、领取租约、生成内容、保存对话消息、渠道投递、系统通知作为同一触发的阶段。用稳定的 `scheduleId + generation + scheduledAt` 建立触发去重；阶段使用固定操作／消息／投递标识并保存确认。

整体区分待执行、执行中、待重试、部分完成、已完成、失败、阻断、错过、取消和结果未知。对话已保存但通知失败要显示部分完成；“加入发送队列”不能显示为送达；结果未知的外部发送先核验回执和去重能力，不能盲目重发。

历史展示计划／实际时间、来源、角色、目标、每个阶段状态、尝试次数、失败原因和下次重试。状态面板从同一账本与关联投递结果统计，失败数不固定为 0，背压不固定为 false。只有存在实际可清理状态时才显示“清除”，操作结果包含实际处理数和未处理原因。

预期提醒面板展示真实未来触发时间；预览执行校验和消息构造，不产生真实发送。保留历史清理设置，默认不自动删除执行历史；清理仅影响允许清理的结束记录，保留活动定义、去重和未决发送记录。

## 主动任务的整合与更名范围

当前 `plugins/proactive/amitia-extension.json` 的 placement 为 device，`src/index.mjs` 使用 `setInterval` 和初始 `setTimeout` 扫描规则，任务历史也保存在插件状态中。这些是必须改接统一底座的真实路径，不是只改标题即可完成。

保留插件的规则编辑、启停、角色提示模板、频率、每日配额、冷却、免打扰、安全与敏感信息限制等业务能力。规则通过统一服务生成 `proactive_task` 定义；Kernel 负责计划、执行租约、重试和历史。插件可以保留规则配置与策略计算，但不能继续用 tickTimer 决定何时独立发出消息，不能把本地 history 当成第二权威执行记录。

到期执行前再次检查当前规则、角色、免打扰、配额及授权。明确用户提醒与自主主动任务的策略差异：主动任务遵守角色的主动频率与免打扰规则，不能把用户明确设定的提醒无条件套用主动闲聊抑制；策略结果都进入同一执行历史。

主动任务界面可保留当前角色插件入口，显示同一账本的规则和任务视图。提醒总览可以按类型筛选用户提醒和主动任务；开发者入口管理技术任务和授权诊断。不同页面操作同一个 ID 和版本，不再各自创建、执行或取消一份记录。

更名覆盖：插件显示名与说明、模块和工具显示文案、手机／桌面 UI Schema、角色入口、开关和配额标签、运行历史和调试页、通知设置及类别显示名、搜索和帮助、安全／时区／关系设置中指代该功能的文案、错误提示及发布说明。插件打包后的用户可见名称也要一致，但产物只能通过源码重新打包生成。

`plugins/proactive` 目录、插件 ID、Host API 标识和 `source=proactive` 等稳定技术标识无需因中文更名随意改动。通知中 `proactive.message` 仍表示一次消息投递事件，可以由“主动任务”产生；用户看到的功能名称改为主动任务。消息正文中的“消息”、发送动作和实际消息类型不能机械替换成“任务”。如果确需修改协议标识，应同步所有发送端、接收端和 Schema，不能留两个执行入口。

本次不增加任意脚本、设备控制或工具自动执行权限。未来扩展主动任务动作时，沿用统一账本、目标适配和明确授权；本次已确认的提醒／主动任务能力完整完成后再定义新增动作范围。

## 插件调用主动任务的接口与权限

宿主开放主动任务能力，具体 API 命名按项目现有 Host API／SDK 约定落地，功能至少包括：

- 创建任务：角色、合法对话、提醒内容或模板、重复规则、时区、开始／结束条件、渠道及系统通知目标。
- 查询列表、详情及下一次执行时间，返回真实 ID、Owner、定义版本与运行状态。
- 更新定义、暂停、恢复、取消和立即执行；变更操作携带预期版本、请求 ID 和幂等标识。
- 查询执行历史、尝试次数、失败／阻断原因，以及消息、渠道和系统通知的分别投递状态。
- 查询当前运行位置的能力和限制；调用失败、所有者不可达或提供者不可用返回明确结果。

所有方法调用同一业务服务和权威账本。插件命令、SDK、HTTP 用户入口和主动任务页面之间不转换成另一种独立任务；修改后各入口看到同一个版本，取消后旧触发不能继续执行。

权限建议按读取、创建、修改／取消和执行分别声明，例如 `proactive_task.read`、`proactive_task.create`、`proactive_task.manage`、`proactive_task.execute`，最终命名与现有能力目录核对后确定。发送渠道、使用角色上下文和系统通知的权限也须独立满足；具备创建权限不意味着自动获得全部发送权限。

宿主从真实插件实例、模块和调用上下文取得身份、Space、角色范围及部署位置，客户端参数不能伪造这些字段。插件默认只能管理自己创建且获授权的任务；操作用户或其他插件的任务，需要明确授予对应资源范围，不设通用绕过接口。

插件创建的主动任务记录真实来源和执行依赖。插件停用、卸载或撤权时，相关任务失去执行资格并被暂停／取消，保留必要的取消回执、去重和历史；插件请求不能取消其他来源的任务。Host API／SDK 由稳定宿主提供，不依赖某个主动任务 UI 插件安装后才获得基础业务能力；来自插件的自定义策略或目标则仍按其实际依赖处理。

云端插件调用时任务保存到确认的云端所有者并由云端执行；设备插件调用受委托 Core 时走真实所有者路由。目标设备离线不被转换成调用成功或本地重复任务。调用结果必须包含保存确认和实际目标位置。

插件验收包含：创建后手机／电脑可见；更新与取消跨入口一致；重复请求不重复注册；越权访问和撤权后执行被拒绝；本地和云端均真实调用；失败及部分投递结果可查询。只增加 SDK 方法名或接口声明不能计为完成。

## 实施顺序与完成标准

先落地 Kernel 权威账本、业务端口和原子创建，再接工具及插件，再接两端页面、消息／通知和状态，最后删除旧读写、轮询及数据来源。实现可以分步骤提交，但最终验收不能停在“新链路可用、旧链路仍并行”。

完成必须同时满足：

- 任意入口创建得到一个可查询、可编辑、可取消且能执行的提醒，保存失败不报告成功。
- 到期发往绑定角色对话；指定渠道和系统通知展示真实分目标结果。
- 一次、每日、每周、每月、指定星期、间隔、时区、暂停恢复和结束条件全部按统一规则执行。
- 同一请求、多设备并发、重启恢复、消息已存而投递失败等场景不重复创建／生成；异常或未知状态明确可见。
- 权限撤销、插件卸载、会话失效、Owner 不可达和版本变化不向错误对象发送。
- 列表、预期提醒、历史、失败、背压和清除动作都来自真实状态。
- 旧业务表没有运行读写，旧 ticker 没有启动，旧界面和假成功路径已删除，历史数据没有进入新系统。
- 本地、设备协同和云端模式均调用同一业务与调度链；云端断开客户端后仍正常执行，重启恢复不重复发送，多主体互相隔离。
- 主动任务名称在两端及插件展示中统一，现有策略功能保留，设备和云端部署有真实入口，独立插件扫描器已退役。
- 插件通过公开 Host API／SDK 真实创建、管理和执行主动任务；资源归属、权限、生命周期与执行结果在两端一致可查。

实现阶段仅运行涉及模块的定向验证。当前进行源码整合，不进行 APK／桌面安装包构建或安装；后续按用户确认的执行范围和项目自动构建规则处理，若用户指定仅源码／暂不构建则跳过。发布、上传和 Git 推送仍需要相应明确授权。

## 实施进度：调度底座

2026-10-14 开始 B02 的基础整合。已修复扫描器重新计算未来时间而越过持久化到期时间的问题；触发生成使用同一数据库事务保存触发和时间游标；手动触发不消耗或更改重复时间游标。

定义与初始状态原子保存，创建参数计算失败不保存半条记录。更新及启停／暂停／恢复按预期代次在事务中执行，状态变更推进代次，使旧待执行触发失去执行资格。执行目标调用前重新检查启用、暂停和代次，执行结束不覆盖已经变更的配置。

恢复首个错过的一次性任务，补发策略增加可配置窗口，移除恢复时只处理前 50 个启用定义的限制。SQLite 领取租约只允许待执行／到期／待重试状态，已完成触发不能被旧线程重新领取。
