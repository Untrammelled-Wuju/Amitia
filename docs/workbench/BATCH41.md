# U-Ai Workbench Batch 41：Coding Agent 证据对账与合并审计约束

## 范围与进度

基于 Batch 40 累计源码开发，优先处理 Coding Worker 从真实测试到人工审批、安全合并及重启恢复的证据一致性。研发覆盖率仍是估算，不等于生产构建和真机验收。

## 本轮源码变更

- 将检查点成功证据的状态验证抽为 `VerifiedTestEvidenceComplete`：必须处于允许的 Go 测试配置，来源修订精确匹配、已记录启动时间、非负执行时长、退出码为 0、测试已通过、输出未截断且拥有有效 SHA-256 格式的输出摘要。
- 检查点人工审批、合并预检、合并审计崩溃恢复和父 Agent 审查投影统一使用上述规则。即使持久化 `Passed=true`，其余证据不完整也不能作为真实测试通过的凭证。
- 合并审计增加身份、分支、提交、计划指纹、actor、状态机字段约束，并在服务端读取时重新以真实目标仓库位置计算计划指纹。
- 原有 `pending` 审计的安全恢复和 `applied` 审计的读取保留兼容，但篡改计划身份或伪造不完整终态时拒绝继续。
- 新增缺失摘要、非零退出码、错误测试类型、审计目标篡改、非法审计状态等回归案例，且保留先前全部累计修改。

## 已验证 / 待验证边界

- 受影响的 `gitworktree` 整包通过 Go race 测试并使用临时真实 Git 仓库，验证审批、预检、恢复和审计读取。
- 父 Agent 审查层的调用接线已经修改并补充源码测试，但因完整 Go 1.26.1 服务依赖未具备，这部分仍待完整编译和真实 HTTP/Agent 运行联调，不得声明为已通过。
- 模块内存储防篡改只是结构和数据一致性校验；没有增加外部签名，不是抵御具有宿主文件写权限的攻击者的密码学完整性保证。
- 完整工程、Flutter Release、Electron/Windows、跨设备及生产性能仍需单独验收。
