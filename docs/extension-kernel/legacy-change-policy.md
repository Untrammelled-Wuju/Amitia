## 二、允许修改范围

冻结期间仅允许以下 6 类修改。详细边界见 `01-system-freeze.md` 第三节。

### 1. 阻塞性缺陷修复

仅允许修复会导致以下问题的缺陷：应用无法启动、扩展系统启动时崩溃、数据损坏、数据丢失、权限绕过、密钥泄露、路径穿越、任意代码执行、MCP 连接导致主程序崩溃、扩展执行导致主聊天链路不可用、无法卸载或恢复扩展、已有功能完全不可用、阻塞后续重构或迁移。

边界：不得借「修复缺陷」名义顺带增加新功能；不得在缺陷修复中引入新产品能力或新数据库表。

### 2. 安全修复

允许处理：包解析安全、归档解压安全、签名校验、Secret 加密、权限校验、作用域越权、插件运行隔离、MCP 认证安全、敏感日志泄露、输入参数验证、SQL 注入、命令注入、路径注入。

边界：安全修复必须保持对现有行为的最小影响，不得借安全修复名义重构旧架构或扩展旧系统职责。

### 3. 回归测试补充

允许增加：单元测试、集成测试、数据库迁移测试、包解析测试、权限测试、MCP 连接测试、Agent Skill 解析测试、Workflow 执行测试、Plugin 生命周期测试、启动恢复测试、卸载清理测试。

边界：测试代码不得推动旧架构继续扩展，不得在测试夹具中引入新产品能力或新扩展类型。

### 4. 可观测性补充

允许增加：日志、Trace、Metrics、调试开关、执行耗时统计、启动恢复日志、权限拒绝日志、数据迁移诊断信息。

边界：新增日志不得记录 API Key、OAuth Token、Cookie、完整聊天内容、用户私密数据、插件 Secret、数据库连接凭据；可观测性不得引入新运行时或新 Registry。

### 5. 迁移辅助能力

允许增加只服务于后续迁移的：只读查询接口、数据导出、状态快照、旧数据扫描、旧资源所有权识别、依赖关系分析、数据一致性检测、临时迁移标记、旧版本数据转换工具。

边界：迁移辅助能力不得成为新的永久业务接口，必须按本文档第六节命名并附带删除计划。

### 6. 文档与注释

允许增加：架构说明、历史兼容说明、弃用标记、迁移说明、风险说明、测试说明、数据表说明、启动顺序说明。

边界：文档与注释不得隐含扩展旧 Manifest v1 或新增旧系统职责的承诺。

## 三、禁止修改范围

以下 8 类修改全部禁止。详细说明见 `01-system-freeze.md` 第四节。

### 1. 禁止新增扩展类型

不得在旧系统新增：新 Skill 类型、新 Plugin 类型、新 MCP 包装类型、新 Workflow 类型、新扩展包 Entry、新 Provider 类型、新 UI 扩展类型、新 Hook 类型。

### 2. 禁止扩展旧 Manifest

不得继续向旧 Manifest v1 增加：新顶层字段、新 Entry 类型、新权限语法、新依赖语法、新 Runtime 字段、新 UI 声明、新 Hook 声明、新 Provider 声明。旧 Manifest 只允许修复解析错误和安全问题。

### 3. 禁止新增旧系统数据库表

不得为旧系统新增：Skill 表、Plugin 表、MCP 表、Workflow 表、Package 表、Hook 表、UI Contribution 表、Provider 表、新的重复审计表、新的重复启用状态表。

确实需要迁移辅助表时，必须满足第六节要求。

### 4. 禁止新增平行 Registry

不得新增：第二套 Tool Registry、第二套 Skill Registry、第二套 MCP Tool Registry、第二套 Plugin Registry、第二套 Workflow Registry、第二套 UI Registry、第二套权限中心、第二套执行器。

### 5. 禁止新增永久兼容层

不得为了新功能增加：新旧字段双写、新旧状态同步、新旧接口桥接、新旧 Registry 双注册、新旧权限双判定、新旧数据双存储。

后续允许存在一次性迁移适配器，但必须可删除并有明确退出条件。

### 6. 禁止增加旧 Plugin 能力

不得继续扩展当前 Go 内置 Plugin 模型，包括：新 Host API、新 Hook、新 Surface、新事件、新定时任务类型、新动态加载方式、新第三方 Plugin 入口。

当前 Plugin Runtime 只允许修复稳定性、安全性和迁移阻塞问题。

### 7. 禁止让 `.amitiax` v1 承担新职责

不得让旧 `.amitiax` 支持：第三方运行时代码、JavaScript、WASM、UI 页面、Electron 扩展、Provider、后台服务、消息渲染器、桌面组件。

这些能力必须在后续 `.amitiax` Manifest v2 中统一设计。

### 8. 禁止前端继续增加分散入口

不得新增：独立 Skill 子页面、独立 MCP 子系统入口、独立 Plugin 子系统入口、独立 Workflow 子系统入口、新的扩展包入口、新的重复运行记录页面。

旧页面只允许修复无法使用、数据错误和安全问题。

## 四、提交类型约束

冻结后，扩展相关提交必须严格遵守以下类型约束。详细说明见 `01-system-freeze.md` 第六节。

### 1. 允许的提交类型

```text
fix(extension):
fix(mcp):
test(extension):
test(mcp):
docs(extension):
refactor(extension-foundation):
migration(extension):
security(extension):
```

### 2. 禁止的提交类型

```text
feat(skill):
feat(plugin):
feat(mcp):
feat(workflow):
feat(package):
```

### 3. 例外条件

例外：除非该功能明确属于新的 Extension Kernel，且不修改旧系统职责。提交者若主张适用例外，必须在提交说明中给出依据并引用对应新系统规划文档。

## 五、提交说明约束

每个涉及旧扩展系统的提交必须在提交信息或关联 PR 中说明以下 8 项。若某项不适用，须明确写「不适用」并说明原因，禁止留空。

1. 修改原因
2. 是否属于缺陷、安全、测试或迁移（须明确分类，可多选）
3. 是否新增字段
4. 是否新增数据表
5. 是否改变已有行为
6. 是否增加兼容层
7. 后续是否需要删除
8. 对新 Extension Kernel 的影响

提交说明须与对应 Pull Request 中按 `.github/pull_request_template_extension.md` 第二节填写的内容保持一致。

## 六、迁移辅助结构命名与删除计划要求

冻结期间允许新增迁移辅助能力，但必须严格满足以下要求，避免迁移辅助结构演变为永久业务功能。

### 1. 命名要求

迁移辅助表必须名称明确带有以下前缀或后缀之一：

- `migration`
- `snapshot`
- `temporary`

例如：`extension_migration_skill_snapshot`、`mcp_temporary_dependency_map`。

不带有以上标识的迁移辅助结构视为违规。

### 2. 删除计划要求

- 必须有删除计划；
- 不承载永久业务功能；
- 在后续迁移步骤中明确清理；
- 迁移辅助结构必须附带删除步骤编号。

### 3. 数据库迁移检查要求

数据库迁移检查要求提交中明确标记以下分类之一：

```text
permanent
migration-only
temporary
```

- `permanent`：永久业务结构，冻结期间禁止新增（属于旧系统职责的）。
- `migration-only`：仅服务于迁移，须在指定迁移步骤后删除。
- `temporary`：临时结构，须在最近一次迁移步骤后删除。

未明确标记的迁移提交视为违规。

## 七、评审流程

涉及冻结范围的 Pull Request 必须按以下流程评审。完整规则见 `01-system-freeze.md` 第七节，评审模板见 [`../../.github/pull_request_template_extension.md`](../../.github/pull_request_template_extension.md)。

### 1. 必查项（13 项）

- 是否增加新产品能力
- 是否扩大旧架构职责
- 是否增加永久兼容层
- 是否增加重复状态
- 是否新增数据库表
- 是否新增 Registry
- 是否新增权限判断
- 是否新增独立生命周期
- 是否直接修改 Manifest v1
- 是否增加新 UI 入口
- 是否影响后续迁移
- 是否包含测试
- 是否有回滚方式

### 2. 直接拒绝条件（9 项）

出现以下任意情况，PR 应直接拒绝：

1. 在旧 Plugin 上增加第三方插件能力
2. 在旧 `.amitiax` 中增加代码运行时
3. 新建另一套 Tool/Skill Registry
4. 新增重复权限系统
5. 新增与现有表功能重复的数据表
6. 通过双写维持新旧系统长期并行
7. 修改旧系统但未提供必要测试
8. 修改核心执行链但未说明迁移影响
9. 将前端页面状态继续绑定到旧系统内部实现

### 3. 评审流程

1. 提交者按 PR 模板第二节填写 8 项必填说明。
2. 评审者按 PR 模板第三节逐项核对 13 项必查项。
3. 评审者按 PR 模板第四节核对 9 项直接拒绝条件，命中任意一项即拒绝。
4. 评审者按 PR 模板第五节核对提交类型是否符合约束。
5. 任意一项不满足时，要求提交者修订后重新提交。
6. 通过后须在 PR 中保留评审记录，便于后续迁移步骤追溯。

## 八、分支策略

### 1. 专用重构分支

建立专用重构分支：

```text
refactor/extension-kernel
```

所有新 Extension Kernel 相关工作应在该分支或其派生分支上进行。

### 2. 旧系统紧急缺陷修复

旧系统紧急缺陷修复应从当前稳定分支单独处理，再选择性合并到 `refactor/extension-kernel` 分支。

- 紧急缺陷修复分支命名建议：`hotfix/extension-<issue>` 或 `hotfix/mcp-<issue>`；
- 修复完成后须按本策略第五节要求填写提交说明；
- 合并到重构分支前须通过本策略第七节的评审流程。

### 3. 禁止事项

- 禁止直接在 `refactor/extension-kernel` 分支上对旧系统进行大规模重构；
- 禁止借紧急修复名义扩展旧系统职责；
- 禁止将旧系统的永久兼容层混入重构分支。
