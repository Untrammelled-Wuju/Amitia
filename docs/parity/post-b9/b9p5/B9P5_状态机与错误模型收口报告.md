# B9P5 状态机与错误模型收口报告

## 1. 执行结果

**状态: PASS**

B9P5成功完成。所有真实状态模型已完成审计，所有B9状态已完成映射，全部Canonical状态Owner明确，无第二套状态系统，无第二套错误Registry新增。

## 2. 为什么需要B9P5

B9重新定义了Runtime/Task/Tool/Permission/Provider/Extension/Model/Voice/Availability等状态枚举，以及一套ERR_*错误Registry。但这些领域在Amitia源码中已经存在成熟的领域状态模型和错误类型。

B9P5的目标不是删除B9协议，而是建立三层架构：

- L1 Domain Canonical State(当前领域真实状态/错误事实源)
- L2 Protocol Projection(对外统一协议状态/错误映射)
- L3 Presentation(Flutter/Web/Desktop/API展示状态)

核心原则：B9协议状态只能作为边界协议、UI归一化或跨端投影；不得成为第二套状态存储、第二套状态机、第二套错误中心。

## 3. 当前状态体系总览

Amitia当前存在24个状态模型，分布于以下领域：

- capability: HealthStatus(5值), ToolState(8字段), ToolResultStatus(4值), ToolContentType(7值)
- tool_execution: observability.ExecutionStatus(15状态权威), execution.ExecutionStatus(12状态入口)
- task_runtime: TaskRunStatus(15状态完整状态机), TaskState(11状态视图), ProcessHostState(8状态进程级)
- extension_runtime: DesiredState(5), ActualState(10), HealthStatus(4), CircuitState(3)
- android_runtime: RuntimeState(13), RuntimeComponentState(9), RuntimeProgressStage(15)
- permission: PermissionDecision(6), GrantIssuer(3), SubjectType(9), ScopeType(10), ApprovalMode(4)
- desktoppet_runtime: RuntimeState(6)

验证结果：所有状态模型均有唯一Owner，duplicateWriterCount = 0。

## 4. Capability Availability

当前Capability Availability由两个核心结构表达：

**HealthStatus** (5值): unknown, ready, degraded, unhealthy, shutdown

**ToolState** (结构体): 包含8个bool字段(Installed, ModuleEnabled, CapabilityEnabled, ScopeAllowed, PermissionGranted, RuntimeReady, DependencyReady)和内嵌的HealthStatus。通过VisibleToModel()和Executable()方法计算工具的可见性和可执行性。

B9 AvailabilityStatus(8值)到ToolState的映射：

- AVAILABLE -> 所有字段为true + Health=ready
- UNAVAILABLE -> Health=unhealthy或shutdown (lossy)
- DISABLED -> !ModuleEnabled 或 !CapabilityEnabled
- PERMISSION_REQUIRED -> PermissionDecision=require_approval
- DEPENDENCY_MISSING -> !DependencyReady
- RUNTIME_NOT_READY -> !RuntimeReady
- DEGRADED -> Health=degraded
- UNSUPPORTED_PLATFORM -> CandidateDecision判定

结论：B9 AvailabilityStatus是ToolState的派生投影，不得创建独立的capability_status数据库表或Store。

## 5. Tool Execution

Tool Execution存在两个相关层：

**执行内核层** (`execution/kernel.go`): 定义了12状态的ExecutionStatus(queued, awaiting_approval, running, retrying, succeeded, failed, cancelled, timed_out, denied, rate_limited, circuit_open, invalid)，作为ExecutionSecurityKernel.Execute的入口参数。

**Observability审计层** (`observability/status.go`): 定义了15状态的ExecutionStatus(created, queued, awaiting_approval, running, retrying, succeeded, failed, cancelled, timed_out, denied, rate_limited, circuit_open, invalid, partially_succeeded, interrupted)，拥有完整的IsTerminal(), IsValid(), IsTransitionValid()方法。

权威判定：observability.ExecutionStatus为权威层，execution.ExecutionStatus是其子集。Execute包的版本仅用于参数传递，不定义独立转换规则。

B9 ToolExecution(11值)到observability.ExecutionStatus映射：7个ONE_TO_ONE，4个NO_MAPPING(VALIDATING, READY, PAUSED, CANCELLING在Kernel中无对应)。B9缺少Kernel实际拥有的retrying, denied, rate_limited, circuit_open, invalid, partially_succeeded, interrupted等独有状态。

## 6. Tool Result

ToolResultStatus是**调用最终结果状态**，不是执行生命周期状态：

ToolResultStatus(4值): success, failed, cancelled, timed_out

这与ExecutionStatus(执行生命周期)属于不同语义层次：

- ExecutionStatus = 执行过程的阶段(queued -> running -> succeeded)
- ToolResultStatus = 调用的最终结果(成功/失败/取消/超时)

B9中无直接对应ToolResultStatus的Protocol定义。必须保持二者的区分，不得合并。

## 7. Task Runtime

Task Runtime拥有Amitia最完整的状态机之一：

**TaskRunStatus** (15状态): created, queued, starting, running, checkpointing, pausing, paused, resuming, cancelling, cancelled, succeeded, failed, timed_out, recovery_required, manual_intervention

终态: succeeded, failed, cancelled, timed_out, manual_intervention

拥有完整的状态转换规则表(IsValidTransition/MustTransition)。

B9 TaskStatus(14值)映射分析：

- 直接映射: CREATED->created, QUEUED->queued, PAUSED->paused, RESUMING->resuming, SUCCEEDED->succeeded, FAILED->failed, CANCELLED->cancelled, TIMED_OUT->timed_out
- 多对一: RUNNING->running/checkpointing/pausing/resuming (lossy), RECOVERING->recovery_required (lossy)
- **需要Domain Split**: PLANNING, WAITING_TOOL, WAITING_PERMISSION, WAITING_USER属于Agent Task/Pipeline域，不在TaskRuntime域中

结论：TaskRunStatus不能被B9 TaskStatus替换。B9中的PLANNING/WAITING_TOOL/WAITING_USER状态属于Agent Planner领域。

## 8. Runtime领域拆分

Runtime状态必须明确拆分为至少三个独立领域：

### Extension Runtime (Desktop/Server端)

DesiredState(5): running, stopped, connected, disconnected, paused
ActualState(10): created, starting, ready, degraded, draining, stopping, stopped, crashed, failed, quarantined

含有B9没有的**draining**(优雅停止中)和**quarantined**(隔离)等独有状态。

### Android Embedded Runtime (移动端)

RuntimeState(13): UNKNOWN, NOT_INSTALLED, INSTALLING, INSTALLED, VERIFYING, STARTING, READY, DEGRADED, STOPPING, STOPPED, REPAIRING, CORRUPTED, FAILED

含有B9没有的**VERIFYING**(校验中)、**REPAIRING**(修复中)、**CORRUPTED**(损坏)等独有状态。

### DesktopPet Runtime (桌面宠物桥接)

RuntimeState(6): disconnected, connecting, handshaking, connected, streaming, error

完全独立的状态体系。

结论：三者属于不同平台/领域，不得合并成GlobalRuntimeStateStore。

## 9. Android Embedded Runtime

Android Runtime由RuntimeStateMachine管理，拥有完整的13状态生命周期。

关键方法：IllegalRuntimeTransitionException校验状态转换合法性。

组件级状态RuntimeComponentState(9值)：多了DISABLED状态，少了REPAIRING/CORRUPTED。

进度阶段RuntimeProgressStage(15值)：用于UI展示的安装/操作进度。

B9 RuntimeStatus只能作为Android RuntimeState的Protocol投影。Android的REPAIRING映射到B9 RECOVERING是lossy的。

## 10. Extension Runtime

由DefaultSupervisor管理，维护Desired/Actual状态对。

核心机制：
- CircuitBreaker(熔断器): closed/open/half_open
- HealthChecker: healthy/degraded/unhealthy/unknown
- RestartPolicy: never/on_crash/on_transient_failure/always_with_limit/manual
- StopReason: manual/drain/crash/update/rollback/disable/uninstall/quarantine/dependency_lost/resource_limit/circuit_open

错误模型包含5个RUNTIME_*错误码和多个instance管理错误。

## 11. Permission Policy与Platform Authorization

**两层语义必须明确区分**：

### Kernel Permission Policy Domain

PermissionDecision(6): deny, allow, require_approval, allow_once, allow_session, allow_persistent

这是Amitia Permission Broker的策略决定，持久化到SQLite(kernel_permission_grants)。

### Platform Authorization State

OS原生权限(Android/Desktop/iOS)由Platform Adapter读取。

B9 PermissionStatus(9值)更像OS/UI授权生命周期，与PermissionDecision语义不同：

- GRANTED在B9中对应Kernel的allow/allow_once/allow_session/allow_persistent (MANY_TO_ONE, lossy)
- DENIED_PERMANENTLY在B9中对应deny(duration=permanent) (通过GrantIssuer判定)

结论：B9 PermissionStatus只能作为UI/API投影，PermissionDecision是策略事实源。

## 12. Provider

B9 ProviderStatus(8值): UNREGISTERED, REGISTERED, INITIALIZING, READY, DEGRADED, UAVAILABLE, FAILED, DISABLED

当前Amitia没有统一Provider状态Store。各Provider(Model/Voice/Storage/Platform)自行注册、自维护健康。

正确做法：B9 ProviderStatus作为Protocol候选，各Provider基于自身health/availability数据投影到B9集合。不得创建ProviderStateStore与现有Provider双写。

## 13. Extension Lifecycle

B9 ExtensionStatus(11值): DISCOVERED, INSTALLING, INSTALLED, ENABLING, ENABLED, DISABLING, DISABLED, UPDATING, UNINSTALLING, FAILED, INCOMPATIBLE

当前Extension Package操作未使用统一状态枚举，而是通过各PackageManager/LifecycleManager的操作返回值/错误表达状态。

正确做法：如果后续需要Extension状态视图，应基于已有Package/Manifest数据计算得出，不得新建extension_status_store与现有操作实现双写。

## 14. Model Request

B9 ModelRequestStatus(9值): CREATED, QUEUED, CONNECTING, STREAMING, WAITING_TOOL, COMPLETED, CANCELLED, FAILED, TIMED_OUT

当前没有独立的ModelRequest状态机。Model Request生命周期由各Chat/LLM Pipeline内部管理。

正确做法：B9 ModelRequestStatus作为Protocol候选，如果后续需要该视图，应基于Pipeline数据计算得出。

## 15. Voice

B9 VoiceStatus(9值): IDLE, LISTENING, TRANSCRIBING, SYNTHESIZING, BUFFERING, PLAYING, PAUSED, INTERRUPTED, FAILED

当前由ASR/TTS/实时通话等多个Provider各自维护状态。

正确做法：通过多Provider Protocol Projection，不得实现GlobalVoiceState。

## 17. Observability与Projection

当前至少存在四个不同层次的状态：

1. **CANONICAL_DOMAIN_STATE**: TaskRunStatus, ActualState, RuntimeState, PermissionDecision等
2. **CANONICAL_DOMAIN_OUTCOME**: ToolResultStatus
3. **DERIVED_STATE**: ToolState (通过8个bool字段计算), TaskState (TaskRunStatus的视图)
4. **OBSERVABILITY_PROJECTION**: observability.ExecutionStatus, AuditOutcome, RuntimeProgressStage

正确流向：

```
Canonical Domain State
        ↓
Projection Function
        ↓
Protocol State (B9)
        ↓
UI/Presentation
```

禁止反向：Protocol State → 写回Canonical Domain State(除非通过Command)

3. Extension/Android/DesktopPet RuntimeState: 不同领域/平台，各自独立

5. runtime_supervisor vs Android StopReason: 不同领域
6. B9 vs Kernel ToolExecutionStatus: Protocol Projection关系
7. Kernel vs B9 PermissionStatus: 策略决策 vs UI投影

真正的重复系统数量: 0

## 25. Permission Error

PermissionDecision是核心策略事实源，其错误处理由调用方返回给ToolExecutor。

Kernel错误域较小(ErrPermissionSnapshotNotFound)，因为权限策略更多体现在deny/allow/require_approval决策而非错误码。

Permission拒绝必须区分:
- Policy Deny(PermissionDecision.deny)
- Scope Deny(scope_denied)
- Approval Denied(审批被拒)
- Permanent Platform Denial(OS永久拒绝)

不得合并为单一ERR_PERMISSION_DENIED。

## 26. Model/Voice/Extension错误

### Model错误

### Voice错误

### Extension错误

## 31. State/Error Guard

建立了14条架构护栏，均为BLOCKER级别：

1. NO_SECOND_STATE_STORE - 禁止创建第二套状态存储
2. NO_PROTOCOL_STATE_AS_DOMAIN_SOURCE - B9状态不能成为事实源
3. NO_STATE_DUAL_WRITE - 禁止同一状态多Store双写
4. PROJECTION_MUST_BE_ONE_WAY - 投影必须单向
5. NO_SECOND_ERROR_REGISTRY - 禁止创建全局Error Center
6. NO_DOMAIN_ERROR_SEMANTIC_LOSS - Protocol不能丢失Domain语义
7. NO_RAW_INTERNAL_ERROR_LEAK - 禁止泄露内部错误
8. RETRYABILITY_OWNED_BY_DOMAIN - Domain拥有Retryable判定权
9. HTTP_MAPPING_OWNED_BY_DOMAIN - Domain拥有HTTP映射权
10. ANDROID_EXTENSION_RUNTIME_SEPARATE - 平台Runtime分离
11. PERMISSION_POLICY_VS_AUTHORIZATION - 策略与OS授权分离
12. TASK_RUNTIME_VS_AGENT_PIPELINE - Task与Agent状态分离
13. STATE_CONFLICT_RESOLUTION - 冲突时Domain优先
14. OWNER_MUST_BE_UNIQUE - Owner必须唯一

适用期限: B10-B154任何新能力。

## 35. 最终结论

B9P5达成所有目标：

1. **各领域真实状态事实源已确定**: 24个状态模型，10个唯一Owner，无重复系统

3. **Tool Execution与Observability层级已明确**: observability为权威层，execution为入口子集
4. **Task Runtime与Agent Task状态已拆清**: REQUIRES_DOMAIN_SPLIT明确3个Agent域状态
5. **Android Runtime与Extension Runtime已拆清**: 不同平台，不同语义
6. **Permission Policy与OS Authorization已拆清**: 策略决 vs UI投影
7. **现有领域错误继续作为事实源**: 33个Error Family，各自维护
