二、现有调度系统盘点(领域 1-6)

2.1 三套并行调度实现(系统 3 — 最严重)

(A) ProactiveCron — 进程级单例

  • 文件:backend/cmd/server/proactive_cron.go
  • 4 个 goroutine:runReminderScanner(10s)、runActiveTaskScanner(30s)、runDailyRegenerator(60s)、runRandomBurstTrigger(60s)
  • 另启动 SafeScheduler.Start()
  • 缺陷:cleanStaleSchedules(:221)定义但无调用方 → 每日计数器永不重置;lastRegenerateDate 内存态重启后重置;panic 自重启无退避

(B) SafeScheduler — Timer 模式

  • 文件:backend/internal/proactive/safe_scheduler.go
  • loop()(:46) 每次计算最早触发时间 → time.NewTimer(delay) → 到点 fireRules()
  • NextRun 未持久化:calcNextFire(:81) 每轮从 DB 读 schedule_cron + random_minutes 重新计算
  • 时区:全程 time.Local(:126);随机种子依赖 now.Unix()/86400(:114)
  • Misfire:仅 window+5min 跳过(:222),无策略枚举

(C) Plugin Schedule Worker — 持久化但无锁

  • 文件:backend/internal/extension/plugin_manager.go(:576 scheduleWorker)
  • 表:extension_schedules(plugin_repository.go:49),支持 once/interval 两种
  • NextRunAt 已持久化,但查询无行锁(:392 WHERE enabled=1 AND next_run_at<=now)
  • 忽略 Timezone 字段:nextScheduleRun(:766) 恒用 time.Now().UTC().Add(duration)
  • 无 IdempotencyKey、无 Lease、无 Misfire 上界

(D) Executor — 死代码

  • 文件:backend/internal/proactive/executor.go
  • ScanAndExecute/ScanRules/ScanReminders 全仓库无调用方
  • 若被误调用将与 SafeScheduler 双重触发同一规则

2.2 Task Runtime — 最成熟的底座(系统 6)

backend/internal/extension/kernel/task_runtime/ 是现有唯一具备完整执行保障的子系统:

  • 持久化:TaskRun/QueueEntry/Checkpoint/Progress/Result 全持久化
  • 租约出队:DequeueTask(leaseOwner, leaseDuration)(queue.go:54)
  • 三级并发限制:global/extension/definition(queue.go:89)
  • 幂等:OperationID + InputHash(models.go:48-53)
  • 检查点恢复:handleCheckpoint(service.go:345),带 hash 校验
  • 启动恢复:StartupRecovery(service.go:638),扫描 7 种非终态任务
  • 三套 Snapshot ID 已贯通:ScopeSnapshotID/PermissionSnapshotID/DependencySnapshotID(models.go:180-182)
  • Generation 机制:Retry +1(service.go:566),Recover ++(service.go:610)

关键缺口:TaskDefinition 无 cron/定时/schedule 触发字段;它是"异步任务运行时"而非"定时调度"。但所有执行保障基础设施可直接复用。

七、关键架构决策

决策 1:Schedule 系统放置位置

由于 FROZEN.md 冻结旧 extension/ 顶层,新 Schedule 必须建在 backend/internal/extension/kernel/schedule/ 目录下,作为 kernel 子系统。

这与 task_runtime、hook、execution 等同级,符合 kernel 架构分层。

决策 2:与 Task Runtime 的关系

Task Runtime 是"异步任务运行时"(请求驱动),Schedule 是"定时调度器"(时间驱动)。二者职责不同:

  • Schedule 负责:计算何时触发 → 创建 Trigger Record → 调用 Target Adapter
  • Task Runtime 负责:执行长耗时任务(可作为 Target 之一)

Schedule 不修改 Task Runtime 核心,但 Task Target 类型会调用 TaskRuntimeService.Enqueue()。

决策 3:旧调度系统处理

三套旧调度系统需分类处理:

  • Plugin Schedule Worker(extension_schedules 表):迁移到新 Schedule,旧表保留只读
  • SafeScheduler + ProactiveCron:保留为系统内部调度(主动消息/提醒),不属于第三方 Extension Schedule
  • Executor(死代码):删除

不把所有 Timer 都迁成 Extension Schedule(MCP Reconnect/Runtime Health/内部 Housekeeping 保留为系统内部)。

决策 4:Clock 抽象

所有 Schedule 逻辑使用 Clock 接口,禁止直接 time.Now()。已有 backend/internal/extension/fake_clock.go 可参考。
